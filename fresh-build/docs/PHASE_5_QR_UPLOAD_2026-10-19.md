# Phase 5 payment QR upload slice — 19 October 2026

The President account screen now accepts a PNG/JPEG QR image for an active UPI or bank account. It shows the selected file and current beneficiary and requires the operator to attest that they scanned the QR and matched its payee. The server requires a live signed-in President or Data Entry session, an active account eligibility response, and a shared limit of five attempts per actor per hour. It bounds the multipart request and image to 5 MiB, fully decodes the image, computes SHA-256, uploads to the private `qr-private` bucket without overwrite, downloads the stored bytes for comparison, registers the digest, and activates an immutable QR version through the actor's RPC. The operation ID fixes the object path for safe retries; different bytes with the same operation ID return a conflict.

Migration 19, `20261018155052_payment_qr_account_eligibility.sql`, provides the narrow signed-in account check before Storage upload. Direct account-table reads remain denied. Activation still checks the account under its lock. The migration was applied to isolated hosted development; a rollback-only role/account check and updated security catalog passed there. Hosted fixture counts returned zero Auth users, accounts, QR versions and Storage objects. Advisors reported 49 intentional no-policy RLS notices, one anonymous and 67 authenticated security-definer notices, 64 unindexed foreign keys, and three unused indexes; the new function is included in the guarded catalog count.

The disposable local stack applied all 19 migrations. All 12 rollback-only SQL fixtures passed; the updated QR role fixture separately passed again for President, Data Entry and Member. A separate issued-session integration run created synthetic President and Member users and an account, then proved Member denial, exact downloaded bytes and digest, same-operation retry, changed-byte conflict, replacement retirement (one active and one retired version), trusted private read, anonymous/member read denial, and zero finance effects. The run reset the local stack. The pure QR checks and route mocks brought the full Node suite to 87 passing tests. Clean `npm ci`, lint, typecheck, format check, web build, Android bundle export and unconfigured HTTP smoke passed.

Limits: the local fixture used a generated image, not a real payment QR. The server verifies image bytes and stored digest; it does not decode a payment payload or prove that the QR pays the selected beneficiary. That remains a human scan and account approval step before real use. Signed-in web UI, hosted Storage end-to-end, private retrieval for approved recipients, pending object cleanup, actual QR/account setup and Storage backup/restore remain open. The hosted project has no real QR or donor consent approval. `npm audit` still reports 22 dependency advisories (7 moderate, 15 high), concentrated in the existing Expo/React Native toolchain; release triage remains open.
