# Guarded payment QR orphan cleanup

**Date:** 24 October 2026 (India time). **Environment tested:** isolated local Supabase with synthetic images and issued role sessions. Migration `20261024222500_qr_orphan_cleanup_claims.sql` adds service-only claim and finish RPCs. A claim requires a real `qr-private` object older than 24 hours, no QR version at that path, and a verified asset record that is also older than 24 hours if present. The claim becomes a tombstone that blocks late registration and activation. An existing QR version, including a retired version referenced by an earlier request, is never eligible.

`backend/ops/qr-cleanup.js` claims the path, removes it through the Supabase Storage API, then finishes only after the database confirms the object and any QR-version reference are absent. The finish step removes an unreferenced verified-asset registry row. If Storage removal or finish fails, the claim remains pending for a later retry; it never silently re-enables activation. A late upload to a removed path remains blocked by the tombstone. Once that new object is 24 hours old, the same guarded removal can run again. The cleanup command is manual; it is not scheduled or enabled on hosted development.

**Operator sequence:** run the read-only `backend/ops/qr_orphan_inventory.sql` query, review the exact candidate and its age, and exclude `registered_missing_object` because it indicates missing evidence rather than a removable object. Run `node backend/ops/qr-cleanup-cli.mjs <asset-path>` to print a dry run. For an approved, reviewed path, set `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `QR_CLEANUP_CONFIRM_PATH` in a private environment, then run the same command with `--execute`. The confirmation value must match the exact path. Record the result and rerun the inventory. The service credential must stay server-side. Storage files are removed through the Storage API, never by deleting `storage.objects` with SQL, as [Supabase documents](https://supabase.com/docs/guides/storage/management/delete-objects).

**Verification:** clean local reset applied all 29 migrations. The real local Storage lifecycle proved a fresh orphan is skipped; an old unregistered orphan is removed; an old registered orphan loses both image and registry row; an old image with a retired, request-referenced QR version is skipped; Member cannot claim a path; claim blocks late registration and President activation; and a late re-upload can be cleaned after aging. All 13 rollback-only SQL fixtures passed, including updated service-only grant and private-table RLS checks. The 136 Node tests, lint, typecheck, formatting, CLI syntax and dry-run checks passed. Final local Auth/QR/asset/claim/Storage counts were `0|0|0|0|0` after the disposable reset.
