# Task 6 — Threat Model, Posting and Recovery Rules

**15 October 2026. Design only; not a completed security assessment or deployment approval.** Trust boundaries: anonymous site ↔ receipt/content handler; APK/browser ↔ authenticated API; Meta ↔ webhook; scheduler ↔ outbox; API ↔ Postgres/Storage; laptop ↔ restore operator; backup worker ↔ Google Drive. Internet requests, member input, donor replies, GPS and uploaded images are untrusted. The server owns identity, verified amount, recipient selection and account balances.

## Threats and mitigations

| Asset/abuse case | Boundary and control | Mandatory verification before release |
|---|---|---|
| Public receipt enumeration or donor data leak | Random ≥128-bit public code; one narrow HTTPS endpoint, bounded responses, rate limits at network and application levels, no indexing/cache of private PDF, no phone/account in PDF. Existing sequential codes remain restricted until migration review. | Guessing/rate-limit/load and IDOR tests; revoked receipt response; inspect PDF metadata and old lookup. |
| Expense self approval, fake payment and silent deletion | Version-bound reviewer P/T split; payment T only after approval; immutable effect and correction lineage; account proof and independent statement reconciliation. Avoid same actor both verifying President request and paying without independent later reconciliation. | Cross-role, self/alternate requester, concurrency, reversal and report revision tests. |
| Laptop takeover or destructive restore | One named data entry employee holds the dedicated restricted login; on replacement, deactivate old account and create a new one. Short session, device/session log and rate-limit; no DB/service key on device. Restore request enters server preflight: manifest signature/checksum, DB+objects completeness, isolated staging, consistency and schema check, backup of live state, atomic cutover/rollback protocol, monitored audit. No extra UI confirmation is required by the user; a failed preflight never affects live data. | Stolen session, previous employee still able to act, wrong archive, corrupt/missing object and rollback drill. |
| Spoofed WhatsApp transaction ID or STOP, duplicate/reordered webhook | Verify provider request authenticity and token, timestamp/payload constraints, unique provider event ID. Transaction ID is a claim; T compares actual bank/UPI. STOP suppresses immediately, including queued sends; exact donor matching, ambiguous replies routed to review. | Signature failure, replay, two numbers sharing ID, paid-text-only, STOP race and provider retry tests. |
| Consent and wrong recipient | Capture affirmative scope/text/time/source; if uncertain, do not message. At send time recheck current consent and recipient number. Template approval and category/cost ledger; never use account credentials in chat. | No-consent/wrong-number/opt-out and template rejection cases. |
| Location spoof, inaccurate GPS, remote organizer marking | Approved exact masjid center, server-side 100 m and local-day policy; fresh foreground position and bounded accuracy; organizer sends own position for manual marks; reject absent coordinates. GPS cannot prove physical presence alone, so retain anomaly review and onsite test. | Fake/old/coarse GPS, midnight boundary, device permission failure, organizer remotely marking. |
| Malicious bill/memo/gallery image | Quarantine upload, size/type/content validation, image re-encode where appropriate, opaque path, private ACL, no script execution, short-lived read permission; publication is explicit. | Polyglot MIME, oversized, cross-user signed URL, unpublished gallery, private memo leak. |
| Offline replay and stale authority | Local encrypted/minimized draft and stable operation ID; online server rechecks actor/current permissions, version and duplicates; no offline posting/approval/GPS attendance. Client displays pending/rejected/conflict, not accepted, until server acknowledgment. | Kill/restart and duplicate sync, deactivated user, two devices and stale amount/QR tests. |
| Missing backups or malicious archive | Encrypted independent database+object archive with manifest, digest, key rotation/escrow policy, restricted Drive folder/scopes and alerting. Daily 30-day/monthly 1-year target; never assume hosted DB backup contains object bytes. | Full restore to isolated instance and file/hash comparison, expired key and Drive outage tests. |
| Old APK bypasses forced update | Enforce minimum supported client version server-side on protected commands; publish signed APK and reachable support/download URL first; preserve package/signing identity. | Old app direct RPC, fresh APK install over old, offline draft retention, rollback test. |

## Transaction boundary recipes

**Common command wrapper:** use `(actor_id, command_type, operation_uuid)` unique in idempotency table with request digest and response ID. Under a database transaction, authenticate current actor, lock target rows (`SELECT ... FOR UPDATE` or equivalent), enforce permission/state/version, insert domain transition and its audit event and outbox item, post immutable ledger effects if and only if warranted, save response, then commit. A retry with same digest returns original response; same key with different payload fails. Retry serialization failures with a bounded limit. Network calls and PDF rendering occur *after* commit from durable queue; callbacks only advance status under unique external IDs. Do not hold DB locks while contacting providers.

**Money:** verify against actual bank/cash source; prevent reuse of transaction reference within source account after normalization. One-to-one posting references and unique operation IDs prevent double credit. If amount differs from a claim, retain both claimed and verified values and verification evidence. For transfer, create paired account effects and transfer ID in one transaction; sum across assets is zero. For partial expense payment, lock approval/version and aggregate prior paid amounts before enforcing ceiling. For cash count, lock task/count, allow exactly one accepted effect. A correction links reversal and replacement, preserves original, reissues/voids receipt as applicable and marks reports needing revision. Business date may differ from created timestamp; reports expose both cutoff and business interval so late postings are visible in a newer revision.

**Recurring money:** never infer funds from text `paid` or the suggested amount. Treasurer-verified actual funds post exactly once to an identified account; any positive verified contribution marks that month contributed and suppresses balance/five-day reminders. Every receipt states the actual verified amount. A suggested-amount edit changes the current month's displayed suggestion and records a version; previously sent request and receipt snapshots remain immutable. Referrer credit must have a unique verified-payment-or-period source, and correction can reverse the derived credit.

**Tasks and meetings:** task cap and FIFO selection use the same parent lock; waitlist promotion is a single transaction, never an optimistic client counter. Meeting roster finalization by the organizer or named data entry employee fallback is allowed only after the full scheduled local date attendance window, locks the meeting, snapshots invite responses/check-ins and queues exactly one absence notice per eligible member. Finalization cannot add a presence event. Correction after finalization creates a new roster version and cancels/clarifies pending notices. Hafiz corrections append an event and update current projection under row lock.

**Outbox and offline:** `message_outbox` and `webhook_inbox` are durable, unique-keyed and stateful (`pending → claimed → sent/failed/dead`), with claim lease expiry, bounded exponential retry and dead-letter review. Re-read consent and active QR immediately before send. Once a provider accepted a send but acknowledgment is lost, reconcile by provider message ID/client reference before retry to avoid duplicate sends. Offline queue stores action type, payload, schema version and operation ID; rejects obsolete version/role, merges no finance data automatically, and never grants success merely because local save worked.

## Migration, test and decision gates

Before Task 7 SQL: inspect hosted migration history/grants/data, legacy role holders and sequential receipts, take verified staging copy, record deterministic migration/rollback order. Use additive new migration files; do not rewrite historical migrations already deployed. Backfill derived state without creating new money. Migrate behind feature flags with report/ledger reconciliation and old-client denial only after APK is actually distributable. Task 8 must execute RLS/storage privilege matrix, duplicate/concurrency posting, report paise reconciliation, webhook/STOP races, GPS physical check, full restore and Android upgrade tests.

System Admin finance access is read-only for support; approval, payment, verification and other business finance writes are not granted by administrator status. One data entry employee owns the dedicated laptop login and may enroll monthly donors with recorded consent; donor `created_by` must remain distinct from the actual `referred_by`, and the laptop role cannot verify payments. The same employee may finalize an unfinalized meeting roster after the attendance window; approved coordinates remain open. Q103 allows a different masjid beneficiary account for a replacement QR, while actual asset/account ownership and pairing remain release inputs. Live Meta, Drive, domain, account and device checks remain separate release gates.
