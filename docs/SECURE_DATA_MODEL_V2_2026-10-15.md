## Conventions and invariants

- UUID primary keys; foreign keys restrict deletion of historical actors and financial records. All amounts are `bigint` integer paise, INR only, positive for source amounts; signed account effects are represented with direction. All commands take a client-generated UUID operation ID, actor is resolved from authenticated subject on the server, timestamps are server generated. Business dates and monthly period keys use `Asia/Kolkata`; UTC timestamps retain the actual instant.
- Ledger balance is derived from immutable `financial_transactions`. A pending claim, count, approval or scheduled donation has no ledger effect. A correction creates linked compensating effects and a new version; original rows remain. Never update/delete posted effects, issue a receipt twice, or mutate a published report PDF.
- Proposed tables below are additive or replacements by views/RPCs. Where old columns/checks enumerate categories or reference types, extend those constraints in one controlled migration before invoking new commands. Do not run destructive backfills against unknown hosted data.

### Monthly contribution amount rule and remaining design barrier

Q101 is settled: any positive Treasurer-verified amount allocated to a donor's month makes that month `contributed`, even if it is below the suggested amount. Issue a separate receipt for exactly each actual verified posting. The suggested amount is not a debt; do not calculate or message a remaining balance. The five-day reminder is eligible only if that month has no verified contribution and donor consent remains valid. A void/reversal must recompute the month from surviving verified postings before reminder eligibility is decided. Q102 is settled: a changed suggestion takes effect in the **current** month's displayed profile immediately, with a new amount version; keep the previously dispatched request's amount snapshot and all verified payments/receipts intact. No supplemental request or balance reminder arises from the change. Overpayments, multiple payments in one month and credit deduplication need explicit transaction tests. Do not enable recurring posting until the account mapping and real database are validated.

## Indexes, privacy and migration

Use `(account_id,business_date,id)` for ledger scans; `(donor_id,period)` and `(status,due_at,id)` for recurring jobs; `(task_id,status,joined_at,id)` for waitlist; `(meeting_id,member_id)` for attendance; `(employee_id,local_date,prayer)` for prayer; `(business_date,created_at,id)` for report ordering. Use partial unique indexes for active grants and current configurations, and CHECKs for positive amounts, period format, status enums, URL/path length and no self reference. Foreign keys for linked ledger and object metadata use `ON DELETE RESTRICT`; raw WhatsApp body is never indexed as a donor search field.

Migration order: inventory hosted/development schema/data and current role holders; snapshot DB and Storage and restore it into isolated staging; introduce new tables and least-privilege policies; backfill provenance and map old roles after holder approval; extend ledger constraints; introduce versioned RPCs and read projections; switch web/APK clients with a minimum-version gate; revoke superseded function execute grants and policies; reconcile every development ledger effect and receipt against both report engines; only then turn on recurring jobs. Never replay finance postings merely to populate new projections. No prior app receipts were issued to donors; keep prelaunch test data private and use only opaque codes for public lookup.
