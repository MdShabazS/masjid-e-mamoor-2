# Masjid E Mamoor 2 — Durable Notification Specification

**Status:** V1 backend foundation implemented for committee-task events
**Scope:** Durable in-app notification records and personal notification RPCs

## 1. Authority and Purpose

Notifications describe authoritative domain events. They do not create,
approve, or replace business state. Committee-task notifications are generated
inside the same trusted PostgreSQL transaction that mutates the task and
appends its activity record.

The durable notification record is the source consumed by future Web, Mobile,
Realtime, and push-delivery phases. Realtime and push delivery are not part of
this phase.

## 2. Durable Model

`public.notifications` stores:

- the recipient application user;
- the actor application user when applicable;
- notification kind, snapshot title, and snapshot body;
- an application target path;
- source domain/type and source entity ID;
- the originating committee-task activity ID;
- trusted metadata;
- read and creation timestamps.

Committee-task notifications preserve both the task ID and activity ID. The
unique recipient/activity/kind key prevents duplicate delivery for one domain
event while allowing later events on the same task.

## 3. Ownership and Privacy

Notification ownership belongs to `application_users`, not `auth.users`.
Clients receive no direct notification-table privileges. RLS is enabled as
defense in depth, with no broad client policies.

Personal RPCs derive the recipient exclusively from
`current_application_user_id()`:

- `list_my_notifications(...)`
- `get_my_unread_notification_count()`
- `mark_my_notification_read(notification_id)`
- `mark_all_my_notifications_read()`

No personal RPC accepts an application-user ID for ownership. Anonymous callers
cannot execute these RPCs. Internal notification creation helpers are not
client-callable.

## 4. Read and Unread Behavior

New notifications are unread (`read_at is null`). Marking one notification read
is ownership-scoped and idempotent. Marking all notifications read updates only
the current application user's unread rows. Listing is newest-first, bounded,
offset-paginated, and may be restricted to unread rows.

## 5. Committee Task Event Matrix

| Task event | Kind | Recipients | Target |
| --- | --- | --- | --- |
| Task created | `task_assigned` | Active assignees | Task detail |
| Assignee added | `task_assigned` | Newly added assignees | Task detail |
| Assignee removed | `task_unassigned` | Removed assignees | `/work` |
| Meaningful details changed | `task_updated` | Existing active assignees | Task detail |
| Progress added | `task_progress` | Other active assignees and active task managers | Task detail |
| Task started | `task_started` | Other active assignees and active task managers | Task detail |
| Task completed | `task_completed` | Other active assignees and active task managers | Task detail |

Task managers are active application users whose current authorization role has
`committee.tasks.assign`. Recipient sets are deduplicated. Users with task-read
permission alone are not notification recipients.

Meaningful task details are title, description, priority, and due date.
Assignment-only changes do not emit `task_updated`. Newly added and removed
assignees do not also receive `task_updated` for the same activity.

## 6. Self-Notification and Noise Control

The activity actor is excluded from every recipient set, including self-
assignment. A manager who is also an assignee receives one notification for a
given activity and kind.

## 7. Atomicity and Idempotency

Each notification references the activity row created by the trusted task
operation. Notification insertion occurs before the operation transaction
commits. A notification failure therefore rolls back task state and activity
state together.

Existing task operation IDs remain the mutation idempotency boundary. Exact
replays return from the existing activity before notification generation. The
notification uniqueness key provides an additional duplicate guard at the
recipient/activity/kind level.

## 8. Presentation Snapshots

Snapshot title/body text is generated by trusted database logic and includes
the task title where useful. Clients do not provide notification text,
recipients, source IDs, or target paths. Notification content must remain
concise and must not expose authentication credentials or sensitive member or
financial data.

## 9. Deferred Phases

The following remain explicitly deferred:

- Web notification center and notification bell;
- Mobile notification center;
- Supabase Realtime delivery;
- OS push delivery and device-token management;
- notification preferences and channel dispatch;
- email, SMS, and WhatsApp delivery.
