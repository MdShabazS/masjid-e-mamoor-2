# Product Acceptance Criteria — Masjid E Mamoor 2

**Date:** 15 October 2026  
**Status:** Task 5 draft. Criteria marked `OPEN` depend on a user or provider decision. These are required behaviors and test evidence, not claims that the implementation passes. IDs connect to `REQUIREMENT_TO_CODE_TRACE_2026-10-15.md`.

## Release-wide gates

1. All public and authenticated web pages use HTTPS; Android release is a signed, installable APK distributed from the current masjid website. A previous released APK upgrades without uninstall/data loss. Server rejects protected commands from unsupported clients while still showing the public download/contact route.
2. Each role's direct route, RPC, Storage object and downloaded export matches the permission matrix. Rejected callers get no record content; changing a URL, UUID or client UI state never escalates access. Verify both Android and web plus anonymous visitor.
3. Every financial test fixture reconciles in paise by account and period: opening + posted inflows − posted outflows ± internal transfers and approved corrections = closing. Pending claims, unpaid expense approvals, unverified cash and donor expected amounts change no posted balance.
4. Every posted command has a stable operation ID; duplicate requests, webhook retries and concurrent users create at most one effect. Visible error/conflict states tell an operator what happened and never claim success before the server accepts the command.
5. Current official WhatsApp templates, India rates and provider approval, local privacy review, physical geofence test, real DB+object restore and a signed APK upgrade are release checks. A passing local UI test alone is insufficient.

## Threat and abuse ledger

| Asset/actor | Plausible abuse | Required control and verification owner |
|---|---|---|
| Public receipts/donor identity | Guessable code enumerates names/amounts | New high-entropy code, hashed attempts, global/network limits, minimal projection; security test before public launch (Tasks 6, 8, 9). |
| Cash and expense approver | Same person records, approves, pays or erases history | Actor separation, row locks, immutable audit/correction, independent reconciliation; Treasurer/President scenario test (Tasks 6, 8). |
| Laptop restore credentials | Stolen data entry employee login or arbitrary device restores/overwrites live data | Server-only secret, named restricted operator session, staged restore, audit, emergency recovery path and drill (Tasks 6, 8, 10). |
| WhatsApp donor inbox | Forged `PAID`/transaction ID, duplicate event or unlawful messaging | Verify webhook/authenticity, persist consent/STOP, bank reconciliation, idempotent inbox/outbox (Tasks 6, 8, 10). |
| Geofence attendance | GPS spoof or false negative from low accuracy | Fresh foreground accuracy/time, organizer fallback with own onsite proof, audit and physical trial (Tasks 6, 8). |
| Offline queue | Replay after reconnect creates duplicate rupees | Unique operation IDs, server transaction, conflict UX and replay tests (Tasks 6, 8). |
| Private bills/payroll/memos | Guessable object path or unsafe image upload | Private buckets, per-object authorization, type/size/content check and limited links (Tasks 6, 8, 9). |

The acceptance suite is deliberately independent of UI colors or exact table names. Task 6 maps each ID to a schema/API operation; Task 8 records pass/fail evidence for web, APK and local database. `OPEN` items are in `TASK_5_DECISION_REGISTER_2026-10-15.md`.
